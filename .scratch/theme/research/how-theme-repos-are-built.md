# how established multi-target theme projects are built

research into tokyonight, rosé pine, catppuccin, kanso, and six minimal/monochrome references, to extract naming, palette, and generation conventions before building a monochrome+one-accent theme that ships to neovim, ghostty, wezterm, tmux, vscode/cursor, a website, and later bat/delta/fzf/lazygit/starship.

---

## 1. tokyonight (folke/tokyonight.nvim)

repo: https://github.com/folke/tokyonight.nvim

**naming**: single repo, `<name>.nvim` (`tokyonight.nvim`). theme name itself is one lowercase compound word, "tokyonight", styled "Tokyo Night" in prose/UI labels. variants are suffixes: `storm`, `night` (previously "Night"), `moon`, `day` — style names, not "dark/light".

**single source of truth**: a Lua table per variant. `lua/tokyonight/colors/storm.lua` defines the base palette (~30 flat keys: `bg`, `bg_dark`, `bg_highlight`, `blue`, `blue0..7`, `comment`, `cyan`, `dark3`, `dark5`, `fg`, `fg_dark`, `fg_gutter`, `green`, `green1/2`, `magenta`, `magenta2`, `orange`, `purple`, `red`, `red1`, `teal`, `terminal_black`, `yellow`, plus a nested `git = {add, change, delete}` table). Other variants are diffs on top: `lua/tokyonight/colors/night.lua` is literally
```lua
local ret = vim.deepcopy(require("tokyonight.colors.storm"))
return vim.tbl_deep_extend("force", ret, { bg = "#1a1b26", bg_dark = "#16161e", bg_dark1 = "#0C0E14" })
```
Semantic roles (`error`, `warning`, `info`, `hint`, `todo`, `bg_visual`, `bg_search`, `diff.add/delete/change`, a `rainbow` array, and a `terminal` ANSI 16-color table with `_bright` variants) are derived at runtime in `lua/tokyonight/colors/init.lua` from the raw hues — e.g. `colors.error = colors.red1`, `colors.hint = colors.teal`, `colors.terminal.black_bright = colors.terminal_black`. So there are two layers: raw named hues (source of truth) → derived semantic roles (computed, not hand-authored per variant).

**generation**: extras are generated, not hand-maintained. Each target has a **Lua generator script** in `lua/tokyonight/extra/<target>.lua` (48 of them — wezterm, ghostty, tmux, alacritty, kitty, iterm, sublime, lazygit, fzf, delta, discord, vim, etc.) that calls a tiny mustache-like `util.template(str, table)`:
```lua
function M.template(str, table)
  return (str:gsub("($%b{})", function(w)
    return vim.tbl_get(table, unpack(vim.split(w:sub(3, -2), ".", { plain = true }))) or w
  end))
end
```
Templates are inline Lua multi-line strings using `${key}` / `${nested.key}` interpolation, e.g. `extra/wezterm.lua` emits a `.toml` string with `foreground = "${fg}"`, `ansi = ["${terminal.black}", ...]`. The whole build is driven by `lua/tokyonight/extra/init.lua`'s `M.extras` registry (maps each target to `{ext, url, label, subdir?, sep?}`), looped over 4 styles × N targets, writing `extras/<target>/tokyonight_<style>.<ext>`. Run via `scripts/build`:
```sh
#!/bin/env bash
nvim -u tests/minit.lua -l lua/tokyonight/extra/init.lua
```
i.e. headless Neovim executing a Lua script — no external build tool, no Node/Python. Ghostty's target extension is `""` (Ghostty theme files have no extension).

**repo layout**: mono-repo. Generated artifacts (`extras/aerc/`, `extras/wezterm/`, `extras/ghostty/`, `extras/tmux/`, ~48 target dirs × 4 styles) are **committed to the main repo** and regenerated by CI/maintainer running `scripts/build` before release, not built at install/CI time by consumers.

**distribution per target**:
- neovim: `colors/tokyonight-<style>.vim` + Lua plugin, installed via any plugin manager (`folke/tokyonight.nvim`).
- wezterm: `extras/wezterm/tokyonight_night.toml` — a `[colors]` TOML block, user copies into `~/.config/wezterm/colors/` or requires it.
- ghostty: `extras/ghostty/tokyonight_night` (no extension) — plain `key = value` lines (`palette = 0=...`, `background = ...`), dropped into `~/.config/ghostty/themes/`. README: *"Create `~/.config/ghostty/themes` and download theme file into `themes` directory. Then in `~/.config/ghostty/config` choose the theme."*
- tmux: `extras/tmux/tokyonight_night.tmux` — a bash-shebang script of `set -g ...` tmux option commands, sourced from `.tmux.conf`.
- vscode: **not in this repo** — separate community repo `enkia/tokyo-night-vscode-theme` (org-transferred to `tokyo-night/tokyo-night-vscode-theme`), published to the marketplace as `enkia.tokyo-night`, with its own hand-maintained `themes/tokyo-night-color-theme.json`.
- web/CSS: `extras/tailwindv4/tokyonight_night.css` — a Tailwind v4 `@theme inline { --color-tokyonight-night-bg: oklch(from #1a1b26 l c h); ... }` block, one `--color-tokyonight-<style>-<role>` custom property per role, with cross-references (`--color-tokyonight-night-error: var(--color-tokyonight-night-red1);`).

**license**: Apache-2.0.

**semantic roles**: no fixed "n roles" spec like catppuccin/rosé pine — it's an open-ended Lua table (~30 raw + ~15 derived semantic aliases + a 16-slot ANSI terminal table). New consumers just add a key.

## 2. rosé pine (github.com/rose-pine org)

org: https://github.com/rose-pine — **154 public repos** (org-of-repos model).

**naming**: org named after the theme (`rose-pine`), each app gets its **own repo named after the app** (`rose-pine/neovim`, `rose-pine/alacritty`, `rose-pine/ghostty`, `rose-pine/starship`, `rose-pine/tmux`, `rose-pine/vscode`, `rose-pine/lazygit`, `rose-pine/yazi`, ~150 more), each repo description is "Soho vibes for `<App>`". The hub/docs repo is `rose-pine/rose-pine-theme` (note: *not* the bare org name — kept separate from the palette/build tooling repos). Palette lives in `rose-pine/rose-pine-palette` (also listed under the friendlier import name `@rose-pine/palette`), the templating CLI is `rose-pine/build` (npm package `@rose-pine/build`), and there's a WIP alternative Go build tool `rose-pine/rose-pine-bloom`. Theme name itself: "Rosé Pine" (capitalized, with accent) in prose, lowercase-hyphenated `rose-pine` for slugs/ids.

**single source of truth**: TypeScript object in `rose-pine/rose-pine-palette`'s `source/index.ts`, one flat object per variant (`main`, `moon`, `dawn` — dark/darker/light), each color has `{hex, rgb, hsl}` (some also an `alpha` sub-variant). Exact role list per variant (15 roles):
```
base, surface, overlay, muted, subtle, text,
love, gold, rose, pine, foam, iris,
highlightLow, highlightMed, highlightHigh
```
`love`/`gold`/`rose`/`pine`/`foam`/`iris` are the 6 accent hues (red/yellow/warm-pink/teal-blue/cyan/purple equivalents, evocatively named after the pine-forest concept, not semantically named "red/yellow/blue"). `base/surface/overlay` are background depth steps, `muted/subtle/text` are three foreground-contrast steps, `highlightLow/Med/High` are three selection/highlight backgrounds. Variants are **fully separate object literals**, not deltas (unlike tokyonight). Build outputs from this repo already include committed `dist/` in nearly every common format: css (plain, `-class`, `-media`, `-tailwind`, each also `-hsl`/`-rgb`), json (hex/hsl/rgb), toml, yaml, and a Tailwind CSS plugin JS. License: MIT.

**generation**: the `rose-pine/build` npm package (`@rose-pine/build`, run via `npx @rose-pine/build`) is a generic **string-templating CLI**: you hand-write a template file shaped like your target's real config, with color values swapped for `$rose`, `$pine`, etc. (default `$`-prefixed variable names, configurable prefix). It supports per-variant custom values inline: `"accent": "$($rose|$iris|$pine)"` expands to different values in `rose-pine.json`/`rose-pine-moon.json`/`rose-pine-dawn.json`, and even non-color strings: `"order": "$(Caffè|Cappuccino|Marocchino)"`. Metadata placeholders (`$id`, `$name`, `$description`, `$type`) are injected too. Output color format is selectable (`hex`, `hex-ns`, `rgb`, `rgb-ns`, `rgb-ansi`, `rgb-array`, `rgb-function`, `hsl*` equivalents). CLI flags: `-t/--template`, `-o/--output`, `-p/--prefix`, `-f/--format`, `-s/--strip-spaces`, `-w/--watch`. Each per-app repo (e.g. `rose-pine/wezterm` if it existed, `rose-pine/starship`) is expected to keep its own template + run `@rose-pine/build` itself — the CLI is invoked **per-repo**, not centrally.

**repo layout**: org-of-repos. Each app repo is small (template + generated output only, no shared code). `rose-pine/neovim` for example has `colors/rose-pine.lua` (+`-moon`/`-dawn`/`-main`), `lua/rose-pine/{config,palette,utilities}.lua`, `lua/rose-pine/plugins/`, and a lualine theme — i.e. neovim highlight-group mapping is still **hand-written Lua**, not generated by `@rose-pine/build` (that tool is for flat key=value/text-templated targets like terminal configs, not for editor highlight-group logic).

**distribution per target**:
- neovim: `rose-pine/neovim` plugin repo, `colors/rose-pine*.lua`, installed via plugin manager.
- ghostty: **no dedicated build in `rose-pine/ghostty`** — its `README.md` states Ghostty ships Rosé Pine **built-in**, sourced from iTerm2-Color-Schemes: *"Ghostty has a built-in theme for Rosé Pine from [iTerm2-Color-Schemes]. Add `theme = dark:Rose Pine,light:Rose Pine Dawn`"*; the repo separately provides a `dist/` folder with plain extensionless theme files (`dist/rose-pine`, `dist/rose-pine-moon`, `dist/rose-pine-dawn`) for manual install into `~/.config/ghostty/themes/`.
- vscode: `rose-pine/vscode`, marketplace extension.
- web/css: `@rose-pine/palette`'s `dist/css/*.css` — plain custom properties and Tailwind config variants, importable directly.
- terminal/tmux/starship/etc: per-repo templates run through `@rose-pine/build`.

**license**: MIT throughout (palette, build, per-app repos).

## 3. catppuccin (github.com/catppuccin org)

org: https://github.com/catppuccin — **362 public repos**, by far the largest org-of-repos.

**naming**: org named after the theme (`catppuccin`, stylized lowercase, IPA pronunciation `/ˌkætpʊˈtʃiːn/` linked in the README). Every port repo is named **after the app in lower-kebab-case** (`catppuccin/nvim`, `catppuccin/vscode`, `catppuccin/ghostty`, `catppuccin/tmux`, `catppuccin/starship`, `catppuccin/bat`, `catppuccin/fzf`, `catppuccin/lazygit` is absent from the port list but similar apps like `catppuccin/delta`, `catppuccin/gitui` exist). Repo description convention (from the style guide): `"<emoji> Soothing pastel theme for <App Name>"`. 4 flavors are named like coffee drinks: **Latte** (light), **Frappé**, **Macchiato**, **Mocha** (dark, darkest).

**single source of truth**: `catppuccin/palette`'s `palette.json` (Deno/TS project, npm-published), one object per flavor with metadata (`name`, `emoji`, `order`, `dark: bool`) and a `colors` map. Exact role list per flavor (26 roles):
```
rosewater, flamingo, pink, mauve, red, maroon, peach, yellow, green, teal, sky, sapphire, blue, lavender,   (14 accent hues)
text, subtext1, subtext0, overlay2, overlay1, overlay0, surface2, surface1, surface0, base, mantle, crust   (12 base/UI steps)
```
Each color entry carries `hex`, `rgb`, `hsl`, `oklch`, and an `accent: true/false` flag. Style guide (`docs/style-guide.md`) maps function → role: Background Pane → `Base`; Secondary Panes → `Crust`, `Mantle`; Surface Elements → `Surface0/1/2`; Overlays → `Overlay0/1/2`; primary Text → `Text`; secondary text → `Subtext0/1`. `docs/specs.md` describes the accents as **two sub-palettes**: a monochromatic gray-purple ramp (base→overlay→text, used for UI) and an analogous rainbow ramp (the 14 hues, used for syntax/accents).

**generation**: `catppuccin/whiskers` — a Rust CLI (`whiskers.catppuccin.com`), templates are `.tera` files (Tera = Rust's Jinja2-like template engine) with YAML frontmatter declaring metadata and iteration:
```
---
whiskers:
  version: "^2.4.0"
  matrix:
    - flavor
  filename: "themes/catppuccin-{{ flavor.identifier }}.conf"
---
palette = 0=#{{ if(cond=flavor.dark, t=surface1.hex, f=subtext1.hex) }}
...
background = {{ base.hex }}
```
(this is `catppuccin/ghostty`'s actual `ghostty.tera`, the exact matrix pattern that drives one template → 4 flavor files). Whiskers supports conditionals (`if(cond=..., t=..., f=...)`), filters/pipes (`overlay2 | mix(color=base, amount=0.2) | get(key="hex")`), and matrix expansion over flavor (and optionally accent color) combinations, writing one output file per combination per the `filename` pattern. CI runs it via a shared reusable workflow, `catppuccin/actions/.github/workflows/whiskers-check.yml@v1`, invoked with `args: ghostty.tera` — i.e. **whiskers itself runs in CI**, not just locally; contributors run it locally during dev, CI re-verifies output is committed and current. Notably `catppuccin/nvim` **also** uses whiskers for its own palette generation (`nvim.tera` → `lua/catppuccin/palettes/{{flavor.identifier}}.lua`, i.e. the Lua palette table itself is a generated artifact, not hand-written), while the actual highlight-group logic remains hand-written Lua (`lua/catppuccin/groups/`).

**repo layout**: extreme org-of-repos. `catppuccin/catppuccin` is the **index/meta repo**: holds the palette definition in prose+images, org-wide docs (`docs/style-guide.md`, `docs/port-creation.md`, `docs/specs.md`), assets, and the showcase list — it is not a package consumers install. `catppuccin/template` is a blueprint repo new ports are cloned from (git-cloned, then `.git` deleted and `git init` run to avoid inherited authorship). `catppuccin/toolbox` bundles port-helper tools; `catppuccin/catwalk` renders a 4-flavor layered screenshot for port READMEs. `catppuccin/vscode` itself has evolved into a **pnpm monorepo** (`packages/catppuccin-vsc`, `catppuccin-vsc-pack`, `catppuccin-vsc-storybook`, `catppuccin-vsc-typegen`, `catppuccin-vscode`) rather than a flat extension repo.

**port-creation / style guide rules** (from `docs/port-creation.md`, MIT-licensed org-wide unless the app forces otherwise):
- repo name = app name in `lower-kebab-case`.
- default branch must be `main`.
- images under `assets/`, prefer `.webp`.
- description = `"<emoji> Soothing pastel theme for <App name>"`.
- GitHub topics: `catppuccin`, `theme`, `<app-name>`.
- preview image generated by `catwalk`.
- no org health files duplicated per-repo (CODE_OF_CONDUCT etc. live once in `catppuccin/.github`).
- workflow: draft in your own repo → open a "Port Review" issue → staff review → adopted into the org, staff co-maintain afterward (contributor isn't obligated to keep maintaining).
- userstyles (Stylus-based website ports) go to the separate `catppuccin/userstyles` repo, not the main flow.

**distribution per target**:
- neovim: `catppuccin/nvim`, `colors/catppuccin-<flavor>.lua`, palette generated via whiskers, highlight groups hand-written.
- vscode: `catppuccin/vscode` monorepo → `packages/catppuccin-vsc/package.json`: `"publisher": "Catppuccin"`, `"name": "catppuccin-vsc"`, `"displayName": "Catppuccin for VSCode"`, `contributes.themes` = 4 entries, each `{label: "Catppuccin Mocha", uiTheme: "vs-dark", path: "./themes/mocha.json"}` (Latte uses `uiTheme: "vs"`).
- ghostty: `catppuccin/ghostty`, single `ghostty.tera` whiskers template → `themes/catppuccin-{flavor}.conf`, plain `palette = N=#hex` + `background =`/`foreground =` keys, matching Ghostty's native config format exactly.
- wezterm: `catppuccin/wezterm` — not inspected in depth, but same whiskers-driven `.lua`/`.toml` pattern as others.
- css/web: `@catppuccin/palette` ships `css/catppuccin.css` with vars named `--ctp-<flavor>-<role>` and `-rgb`/`-hsl` suffixed variants for alpha compositing, e.g. `color: var(--ctp-mocha-text); background: rgba(var(--ctp-macchiato-base-rgb) / 0.9);` — importable via npm, jsdelivr, or unpkg.
- tmux/fzf/bat/delta/starship/lazygit equivalents: all separate `catppuccin/<app>` repos, generated the same whiskers way where the target format supports flat templating.

**license**: MIT for the org and nearly all ports (exceptions noted explicitly, e.g. `catppuccin/cursors` due to upstream cursor-theme licensing).

## 4. kanso (webhooked/kanso.nvim)

repo: https://github.com/webhooked/kanso.nvim

**lineage**: explicitly "an elegant evolution of the original Kanagawa theme" (per its own description) — its internal module layout is a near-exact structural clone of `rebelot/kanagawa.nvim` (`lua/kanso/{colors.lua, highlights/{editor,init,lsp,plugins,syntax,treesitter}.lua, lib/{color,hsluv}.lua, themes.lua, utils.lua}` mirrors kanagawa's `lua/kanagawa/...` 1:1), just renamed. No separate "kanso-org"; it is a **single mono-repo**, same shape as tokyonight/kanagawa.

**naming**: `<name>.nvim` pattern, theme name "Kansō" (lowercase "kanso" in code/slugs), variants named `ink`, `mist`, `pearl`, `zen` (mood words rather than dark/light labels).

**how it ships ports**: identical mono-repo + committed `extras/` pattern to tokyonight/kanagawa — `extras/{alacritty,foot,ghostty,iterm,kitty,opencode,st,urxvt,warp,wezterm,windows-terminal,yazi,zathura,zellij}/kanso-<variant>.<ext>`, one file per variant per target, committed directly (no `lua/kanso/extra/*.lua` generator scripts visible in the tree — so either hand-maintained, or generated by an uncommitted/local script, unlike tokyonight's committed generator layer). License: MIT.

## 5. minimal/monochrome-ish references

**vesper** — https://github.com/raunofreiberg/vesper (MIT). Smallest possible shape: no `lua/`, no `extras/`, just `package.json` + `themes/Vesper-dark-color-theme.json`, a single-file VS Code extension. Ships to exactly one target (VS Code marketplace); no org, no ports repo. Its actual palette is a strong proof of the "monochrome + one accent" pattern the user wants: distinct colors used are almost entirely grays (`#101010` → `#FFFFFF` in ~7 steps) plus **exactly one accent pair** — mint green `#99FFE4` (strings/highlights) and orange `#FF7300`/`#FFC799`/`#FFCFA8` (keywords/warnings), with a single soft red `#FF8080` reserved for errors. Community ports to other tools exist as unofficial, unaffiliated repos (not an org).

**oscura** — https://github.com/narative/oscura (MIT), published to the VS Code marketplace as `Fey.oscura` ("Oscura Theme" / "Oscura" by publisher Fey — narative is the org, Fey is the visible marketplace author). Repo shape: `package.json` + `themes/oscura-dusk.json` + `themes/oscura-midnight.json`, no `lua/`/`extras/` — single-target, hand-maintained, matching vesper's minimalism. Palette is dark grays (`#0B0B0F`→`#E6E6E6`) plus a slightly wider accent set than vesper: blue `#479FFA`, teal/green `#4EBE96`/`#54C0A3`, red `#FF5C5C`/`#D84F68`, yellow `#D2D714`/`#EAEC8A`, orange `#F6B98B` — each accent still pinned to one syntax role rather than spread across a rainbow. Community ports (e.g. `vinitkumar/oscura-vim`) exist as separate, unaffiliated single-purpose repos, not an official org.

**flexoki** — https://github.com/kepano/flexoki (MIT). The opposite extreme from vesper/oscura: one giant mono-repo with a **per-app top-level directory** for ~40 targets (`vscode/`, `alacritty/`, `kitty/`, `wezterm/`, `helix/`, `tmux/`, `zellij/`, `gtk/`, `intellij/`, `xcode/`, `discord/`, `telegram/`, `fish/`, `zed/`, `css/`, even `affinity/` and `oomox/`), each with its own README and hand-authored theme file(s) in that target's native format — almost none of it templated. The only generation machinery is `_generators/` (a small TypeScript project, `npm i && npm run build`, sources in `src/{color,iterm2,palette}.ts`) which appears to derive iTerm2/palette-format exports from a canonical palette definition; everything else (VS Code JSON, Sublime, etc.) looks hand-ported per directory. Name style: "Flexoki" — one invented word, capitalized in prose, lowercase in file/dir names.

**vague** — https://github.com/vague2k/vague.nvim (MIT, "main" default branch). Neovim-only core repo (`colors/`, `lua/vague/`); extras for other tools are pushed out to a **separate GitHub org**, `vague-theme` (per its own README), rather than committed extras/ in the nvim repo — a third structural option (org exists, but only for ports, with the "flagship" editor theme staying a plain single-purpose repo). Palette (`lua/vague/config/internal.lua`) is the cleanest semantic-role vocabulary example: no evocative hue names at all — every key is already a UI/syntax function: `bg, inactiveBg, fg, floatBorder, line, comment, builtin, func, string, number, property, constant, parameter, visual, error, warning, hint, operator, keyword, type, search, plus, delta`. Only 4 colors are conventionally "hued" (`error` pink-red `#d8647e`, `warning`/`delta` orange `#f3be7c`, `hint` blue `#7e98e8`), everything else — `builtin`, `func`, `string`, `number`, `property`, `constant`, `parameter`, `operator`, `keyword`, `type` — is a **desaturated near-gray tint**, which is the exact "how do low-saturation themes still cover 10 syntax roles" trick: same hue family, different lightness/desaturation, not different hues.

**zenbones** (zenbones-theme/zenbones.nvim, MIT) — a *family* mono-repo shipping ~19 related colorschemes (`zenbones`, `zenwritten`, `zenburned`, `neobones`, `nordbones`, `rosebones`, `tokyobones`, `kanagawabones`, `seoulbones`, `duckbones`, `forestbones`, `vimbones`, `randombones` — all named `<inspiration>bones`, riffing on the original vim `bones.vim`/Jan Warchoł "zenbones" concept of contrast-based, mostly-monochrome schemes with the terminal's own ANSI colors reused for accents). Each theme is `lua/<name>/{init.lua, palette.lua}` plus a light/dark `specs/{dark,light}.lua`. **Generator approach**: uses `shipwright` (`lua/zenbones/shipwright/`), a Lua build-pipeline framework run inside Neovim — `runners/<target>.lua` files declare a pipeline of `run({specs, p, term}, transform_fn, format_fn, {prepend, header}, {overwrite, "extras/<target>/<name>"})`; e.g. `runners/ghostty.lua` uses a `$key`-style string template (via a `helpers.apply_template`) fed by `transform.colorscheme_to_term_colors` which derives generic `fg/bg/cursor_fg/cursor_bg/selection_fg/selection_bg` plus the 16 ANSI names from the already-resolved Vim highlight specs (`specs.Normal.fg`, etc.) — i.e. it **derives terminal colors from computed editor highlight groups**, rather than from a separate flat palette table. This is a materially different generation strategy from tokyonight/catppuccin/rosé pine (which generate everything from the *raw palette*): zenbones generates from the *rendered colorscheme*.

**kanagawa** (rebelot/kanagawa.nvim, MIT) — the direct ancestor kanso.nvim evolved from. Mono-repo, `lua/kanagawa/{colors.lua, highlights/*, lib/{color,hsluv}.lua}`, extras committed directly under `extras/<target>/kanagawa[-variant].<ext>` for ~18 targets (alacritty, base16, broot, emacs, fish, foot, ghostty, gogh, hyprland, iterm, kitty, mintty, pywal, sway, tmTheme, wezterm, windows-terminal, xresources) with **no visible `lua/kanagawa/extra/*.lua` generator layer** — extras appear hand-maintained/community-contributed rather than templated from the Lua palette. Its palette (`lua/kanagawa/colors.lua`) uses evocative Japanese-painting names (`sumiInk0..6`, `waveBlue1/2`, `autumnGreen/Red/Yellow`, `oniViolet`, `crystalBlue`, `sakuraPink`, `dragonBlue`, etc.) rather than semantic or generic-hue names — semantics (`fg`, `bg`, `comment`, `error`) are assigned later in `theme.lua`/highlight files. Distinctively, the repo also ships a standalone `palette.py` — a k-means/Lab-colorspace **image-color-extraction script** (`matplotlib`+`scikit-image`+`scikit-learn`) used by the maintainer to derive candidate palette colors from reference artwork; this is a one-off design tool, not part of the extras build pipeline.

## synthesis

### (a) mono-repo-with-generated-extras vs org-of-repos-with-a-templating-tool

**mono-repo + committed generated extras** (tokyonight, kanso, kanagawa, zenbones, flexoki-ish): one repo, one Lua/JS/TS script per target under `lua/<name>/extra/*.lua` or `shipwright/runners/*.lua`, run headlessly (`nvim -l script.lua`, or `npm run build`) and the **output committed to git**, so `git blame`/diffs show drift, and consumers never run a generator — they just grab `extras/<target>/<file>`. Cost for a solo dev: **low to start** (one repo, one CI job, no cross-repo coordination, no org to administer), but the generator scripts themselves are bespoke Lua/TS and grow linearly with target count (tokyonight has 48 of them) — each new target is "write one more `.lua` file with a string template," which is easy but 100% manual per format quirk. Discoverability suffers slightly (users have to know to look in `extras/`, not a top-level "install for X" page), but there's exactly one place to open a PR.

**org-of-repos + templating CLI** (catppuccin/whiskers, rosé pine/build): a real templating language (Tera for catppuccin, custom `$var` substitution for rosé pine) decouples "what a target's config file looks like" from "how the palette is defined," and each port lives in its own discoverable, independently-versioned, independently-issue-tracked repo with its own README/screenshot/marketplace listing. This scales far better socially (362 catppuccin repos, mostly community-contributed and co-maintained per `docs/port-creation.md`'s explicit "we don't expect you to keep maintaining it" promise) but costs **much more upfront**: you need a template engine or CLI (whiskers is a whole Rust project with its own release cycle), an org to administer, a `template` blueprint repo, a style guide, a submission/review workflow, and shared CI actions (`catppuccin/actions`). For a solo dev shipping ~7 targets, this is overkill unless you specifically want other people's PRs to land as new sibling repos later.

**recommendation for a solo dev at "nvim + ghostty + wezterm + tmux + vscode + web + maybe bat/delta/fzf/lazygit/starship" scale**: the tokyonight/kanso shape (mono-repo, `extras/` committed, one generator script per target, `${var}` string templating, no external template-engine dependency) gets 90% of catppuccin's benefit at a fraction of the setup cost — it's the shape kanso.nvim itself chose when evolving from kanagawa specifically because it needed multi-target output without org overhead.

### (b) minimum role vocabulary for monochrome + one accent

Across every source studied, "monochrome" themes never actually go full grayscale for syntax — they keep a **small, fixed** set of hued roles and spend the rest of their palette on lightness/desaturation steps of the base neutral. The pattern, concretely:

- **vesper**: near-total grayscale UI (7ish gray steps `#101010`→`#FFFFFF`) + exactly 2 hued roles: mint `#99FFE4` (strings/one "positive" accent) and orange `#FF7300` family (keywords/warnings), + one extra soft red `#FF8080` reserved solely for errors. That's **3 hues total** riding on top of a gray ramp.
- **oscura**: gray ramp (`#0B0B0F`→`#E6E6E6`) + **5 hued roles**: blue (functions/info), green/teal (strings), red (errors), yellow (constants/warnings), orange (numbers) — each hue used for exactly one syntax category, never blended into a rainbow.
- **vague.nvim**: the cleanest model — of ~22 named roles, only **4 are conventionally saturated hues** (`error` red-pink, `warning`/`delta` orange, `hint` blue); everything else that "needs" a distinct syntax color (`builtin`, `func`, `string`, `number`, `property`, `constant`, `parameter`, `operator`, `keyword`, `type`) is a **desaturated near-gray tint differentiated by hue-lean and lightness, not saturation** — e.g. `func = "#c48282"` (warm gray-rose), `keyword = "#6e94b2"` (cool gray-blue), `type = "#9bb4bc"` (gray-cyan). This is exactly the technique to steal: give every syntax role a color, but pull saturation down to near-gray for "structural" roles (keywords, types, operators, punctuation) and reserve real saturation for the roles that must pop (errors, warnings/diffs, one accent-carrying role like strings or links).

**minimum viable role set for a monochrome+accent theme** (synthesizing rosé pine's 15 + catppuccin's 26 + vague's 22 down to what every target actually needs):
- **surface ramp** (3–4 steps): `base`/`bg`, `surface`/`bg-dark` (panels, popups), `overlay`/`bg-highlight` (selection/line-highlight), optionally `crust`/`bg-darkest` (statusline/borders).
- **foreground ramp** (3 steps): `text`/`fg` (primary), `subtle`/`fg-dark` (secondary/comments), `muted`/`comment` (dimmest, line numbers).
- **the one accent**: used for the cursor, primary UI highlight (active tab, mode indicator, links, `git.add`), and doubles as `hint`/`info` in diagnostics — this is your lime.
- **4 semantic non-accent hues, kept low-saturation** unless truly needed: `error` (red, allowed full saturation — it must alarm), `warning` (amber/orange, semi-saturated), `string`/`ok` (can reuse muted green or reuse the accent), `diagnostic-info` (can reuse accent or a desaturated blue). Keywords/types/operators/punctuation can all safely be gray-tinted variants of the foreground ramp rather than separate hues (vague's approach) — this is what keeps a monochrome theme from becoming a rainbow while still satisfying tree-sitter/LSP semantic-token queries that expect *some* differentiation.
- **ANSI 16-color terminal table** is mandatory for tmux/wezterm/ghostty regardless of "monochrome" intent — tokyonight's `terminal = {black, red, green, yellow, blue, magenta, cyan, white, *_bright}` structure is the template to copy; map `red`→error, `green`→accent-or-string, `yellow`→warning, `blue`/`magenta`/`cyan`→shades of the single accent or the gray ramp so the terminal doesn't look rainbow either.

### (c) exact file formats/paths per target

| target | file/path | format | source |
|---|---|---|---|
| **neovim** | `colors/<name>.lua` (or `.vim`) + `lua/<name>/...` | Lua table → `vim.api.nvim_set_hl` calls | tokyonight `colors/tokyonight-storm.vim`, kanagawa/kanso same pattern |
| **ghostty** | `~/.config/ghostty/themes/<name>` (no extension) | plain `key = value` lines: `palette = N=#hex` (0–15), `background =`, `foreground =`, `cursor-color =`, `selection-background =`, `selection-foreground =`, `split-divider-color =` | tokyonight `extra/ghostty.lua`, catppuccin `ghostty.tera`; also: Ghostty bundles themes **built-in** by pulling from `mbadolato/iTerm2-Color-Schemes`' `ghostty/` directory — getting a theme "built into" Ghostty means submitting an `.itermcolors` (or equivalent) to that repo, per rosé pine's README |
| **wezterm** | `colors/<name>.toml` in wezterm config dir, or inline `require` | TOML: `[colors]` block with `foreground`, `background`, `cursor_bg/fg/border`, `selection_bg/fg`, `ansi = [8 hex]`, `brights = [8 hex]`, `[colors.tab_bar]` + nested active/inactive/hover tables | tokyonight `extra/wezterm.lua` (verbatim template shown above) |
| **tmux** | sourced `.tmux` / `.conf` file (`source-file ~/.tmux/theme.tmux` in `.tmux.conf`) | shell script of `set -g <option> "fg=#hex,bg=#hex"` / `set -g status-*` commands, not a declarative format | tokyonight `extra/tmux.lua`, zenbones `extras/tmux/*.tmux` |
| **vscode/cursor** | `package.json` `contributes.themes[]` entries pointing at `./themes/<name>.json` | VS Code theme JSON: top-level `colors` (workbench UI hex map) + `tokenColors[]` (TextMate `scope`/`settings.foreground`) + optionally `semanticTokenColors` | catppuccin-vsc `package.json` (`publisher: "Catppuccin"`, `uiTheme: "vs-dark"`/`"vs"` for light), vesper/oscura single-file examples |
| **css/web** | a `.css` file with `:root { --name-role: value; }` or per-scope selectors | CSS custom properties, often shipped in multiple color-space variants (`-hsl`, `-rgb` suffixes for `rgba()`/`hsla()` composition), sometimes a `@theme inline` Tailwind v4 block mapping `--color-<name>-<role>` to `oklch(from <hex> l c h)` | catppuccin `@catppuccin/palette` css (`--ctp-mocha-text`), rosé pine `dist/css/*.css`, tokyonight `extra/tailwindv4.lua` |
| **bat** | `--theme` looks up a `.tmTheme` (Sublime Text format) registered via `bat cache --build` from `$BAT_THEME_DIR/themes/` | TextMate `.tmTheme` XML/plist | tokyonight ships `extras/sublime/*.tmTheme` reusable for bat; catppuccin has `catppuccin/bat` and `catppuccin/sublime-text` as separate repos |
| **delta** | entries in `~/.gitconfig` under `[delta "<name>"]` or a standalone include file | git-config `.gitconfig`/`.ini`-style key=value (`minus-style`, `plus-style`, etc, as hex or named colors) | tokyonight `extras/delta/tokyonight_night.gitconfig` |
| **fzf** | shell snippet exporting `FZF_DEFAULT_OPTS="--color=fg:#...,bg:#...,..."` | shell script (`.sh`) | tokyonight `extras/fzf/tokyonight_night.sh`, catppuccin `catppuccin/fzf` |
| **lazygit** | `~/.config/lazygit/config.yml` theme block, or a separate included yml | YAML | tokyonight ships both `.conf` and `.yml` under `extras/lazygit/` |
| **starship** | palette table inside `starship.toml`, referenced via `palette = "<name>"` | TOML | rosé pine and catppuccin both have `starship` repos generating a `[palettes.<name>]` TOML block |
